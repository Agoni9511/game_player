## 2. 项目目录

```text
peiwan-platform/
├─ .tools/                       # 项目自带 JDK 21 和 Maven 3.9
├─ admin-web/                    # Vue 3 / TypeScript 运营管理后台
├─ backend/                      # Spring Boot 服务端
├─ backend/data/uploads/         # local 存储模式下的上传文件
├─ database/                     # MySQL 8 全量建库和菜单权限种子脚本
├─ docs/                         # 交接、完整业务流程及部署资料
├─ miniapp/                      # Uni-app 双身份微信小程序
└─ use-tools.ps1                 # 加载项目内 JDK/Maven
```

后端仅使用 MySQL Profile，连接 `peiwan_platform` 数据库，不再集成 Flyway。当前服务器数据库从 V51 更新时依次执行 `database/03_incremental_business_data.sql` 和 `database/04_customer_service_ticket.sql`，不重复执行全量建库脚本。

文件存储默认使用 `local` 模式。后端会加载已被 Git 忽略的 `backend/src/main/resources/application-private.yml`，填写 MySQL、管理员、JWT 和 COS 配置并重新打包后，现有上传接口会切换到腾讯云 COS；部署目录下的 `backend/config/application-private.yml` 可作为更高优先级的外部覆盖。完整说明见 `backend/README.md`。

## 3. 开发环境与启动

### 3.1 技术版本

- JDK：21.0.12 LTS
- Maven：3.9.16
- Spring Boot：3.5.10
- 管理端：Vue 3、TypeScript、Vite、Art Design Pro
- 管理端包管理：pnpm 10（可通过 `npx` 调用）
- 小程序：Uni-app / Vue 3 / TypeScript
- 后端端口：8080
- 管理端端口：3006

### 3.2 Windows 启动

在 `peiwan-platform` 目录加载项目工具：

```powershell
. .\use-tools.ps1
```

启动后端：

```powershell
Set-Location .\backend
mvn spring-boot:run
```

本地便携版 MySQL 8.0.43 可通过项目根目录脚本启动和停止：

```powershell
.\start-mysql.ps1
.\stop-mysql.ps1
```

MySQL 连接密码从当前 Windows 用户的 `DB_PASSWORD` 环境变量读取，不提交到 Git。

启动管理端：

```powershell
Set-Location .\admin-web
npx --yes pnpm@10 install
npx --yes pnpm@10 dev
```

访问 `http://localhost:3006`。开发代理配置在 `admin-web/.env.development.local`，`/api` 和 `/uploads` 默认转发到 `http://localhost:8080`。

启动微信小程序开发构建：

```powershell
Set-Location .\miniapp
npm install
npm run dev:mp-weixin
```

微信开发者工具导入 `miniapp/dist/dev/mp-weixin`。稳定开发模式构建可运行：

```powershell
npm run build:mp-weixin:dev
```

小程序请求地址位于 `miniapp/src/config/env.ts`。真机不能通过 `127.0.0.1` 访问电脑后端，需要配置电脑局域网 IP，并开放 8080 端口。自定义导航栏源文件位于 `miniapp/custom-tab-bar/`，构建脚本会同步到输出目录。

### 3.3 固定开发账号

本地开发账号密码统一为 `123456`：

| 场景 | 账号 | 说明 |
| --- | --- | --- |
| 管理后台 | `admin` | 超级管理员，拥有全部后台权限 |
| 小程序用户端 | `customer` | 普通用户，可测试商品、订单和钱包 |

初始化逻辑位于 `backend/src/main/java/com/peiwan/platform/system/BootstrapData.java`。弱密码和自动校正测试账号只允许用于本地开发，生产环境必须改用安全初始化方案。

## 6. 当前已实现范围

### 6.1 系统、资料和准入

- 用户、角色、菜单、按钮级权限和登录/操作日志；
- 游戏、区服、段位、位置、陪玩标签和陪玩等级；
- 陪玩师资料、游戏资料、媒体资料、审核和工作状态；
- 普通用户提交入驻申请，后台查看并人工跟进；
- 统一文件上传、local/COS 可切换存储及图片/音频/视频/PDF 支持。

### 6.2 商品和价格

- 商品分类、基础服务、单项服务商品和平台套餐；
- SPU/SKU、库存、购买数量、所需陪玩人数、每人价/整单价；
- 按游戏和陪玩等级配置基础服务单价，SKU 价格作为兜底；
- SKU 承诺规则及下单时不可变的订单承诺快照；
- 草稿、上架、下架、复制和完整性校验。

套餐按 SKU 固定整单价计价，不累加基础服务价格。单项服务在选择等级或指定陪玩师时优先使用基础服务等级单价，否则使用 SKU 兜底价。

### 6.3 订单、支付和派单

- 统一交易订单承载陪玩服务和钱包充值；
- 用户自助下单和后台代下单共用同一套计价校验；
- 商品、SKU、价格、游戏资料和承诺规则下单快照；
- 钱包现金/赠送余额支付、模拟微信支付、幂等支付和取消退款；
- 支付后自动指定派单或公开抢单；
- 多人逐个接单、满员状态迁移、候选关闭和后台补充派单。

`pw_order_member` 是订单成员归属的唯一来源。派单任务的 `accepted_player_id` 仅为兼容字段，不代表一张订单只有一名陪玩师。

### 6.4 履约和服务变更

- 每位当前在役成员独立开始、提交完成数量/说明/凭证并接受后台审核；
- 全部当前在役成员审核通过后进入用户确认，确认或超时后完成；
- 用户申请暂停/继续，后台审核后切换状态并记录暂停区间；
- 用户或当前成员发起单成员转单，后台审核后由接替人确认；
- 不可变的逐人转单链，支持 `A+B → C+B → D+B`；
- 用户或当前成员发起炸单，后台审核后终止服务、退款并认定责任；
- 正常售后申请、重新服务和协商关闭。

暂停申请、继续申请、转单和炸单统一进入服务变更审核，但各自遵循独立状态和资金规则。

### 6.5 结算和财务

- 订单完成后只抽佣一次；
- 剩余金额按已完成成员等分，最后一位承接舍入尾差；
- 转单成功结单时，每个发生转出的成员按订单基础单价扣 16%，款项进入平台账本；
- 炸单审核通过时，最终在役成员每人按订单基础单价承担 20%；
- 陪玩师账户、不可变账户流水、提现申请和后台审核；
- 财务中心统一查询交易支付、平台账本、用户钱包、陪玩师账户和订单结算。

支付流水、账户流水、结算明细和平台账本属于不同会计层次，不能直接相加计算营业额。

## 7. 当前实现边界

以下内容尚未完整实现：

1. 真实微信支付下单、回调验签、真实退款回调和对账；
2. 提现审核后的真实支付机构打款及敏感收款账号加密；
3. 商品独立的提交审核/审核通过状态；
4. 暂停区间从有效履约时长、超时、结算和售后计算中扣除；
5. SKU 承诺的自动进度核销、未达标判定和自动补偿；
6. 售后部分退款和独立退款处理结果；
7. 入驻申请自动转陪玩师档案或自动审核，目前仍需人工跟进和后台录入；
8. 商品有效天数消费逻辑和按用户历史订单执行限购；
9. 待付款订单超时自动关闭任务；
10. 转单 16%、炸单 20% 的后台规则配置；
11. 对后台人工开始/完成订单的生产级限制、强制原因和强化审计；
12. 生产 MySQL 增量迁移、对象存储、安全扫描、日志监控和完整生产配置验收。

另外，当前只按陪玩师通过的游戏和等级筛选候选人，没有保存“陪玩师能提供哪些具体基础服务”的精确能力关系。同一游戏内需要精确服务匹配时，仍需运营人工控制。

## 10. 后续开发约束

- 数据结构变更从 V52 开始，使用独立的 MySQL 增量 SQL；当前为 `database/04_customer_service_ticket.sql`；
- 订单成员查询必须以 `pw_order_member` 为准；
- 历史订单展示必须使用订单快照，不能重新依赖实时商品、SKU 或承诺配置；
- 新菜单或按钮必须同时更新数据库菜单、角色授权、服务端权限校验和前端权限判断；
- 支付、退款、结算、责任扣款和提现必须保留幂等键与不可变流水；
- 业务规则变化时同步更新 `BUSINESS_FULL_FLOW.md` 和本交接文档，避免重新出现多个冲突口径。
