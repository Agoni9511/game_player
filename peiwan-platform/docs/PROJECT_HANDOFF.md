## 1. 交接结论

项目已经完成管理后台、RBAC、陪玩师资料、商品与套餐、用户订单、钱包模拟支付、派单接单、履约、售后和陪玩师结算的基础闭环。微信小程序已具备用户端与陪玩师端双身份页面，当前适合继续完善“指定陪玩”和“陪玩师个人服务”，不建议立即接真实支付。

当前主链路：

```text
用户/角色/权限
  → 游戏、位置、标签
  → 陪玩师入驻资料与审核
  → 商品分类、基础服务
  → SPU/SKU、平台套餐
  → 创建订单、确认收款
  → 指定派单/公开抢单
  → 陪玩师接受
  → 开始服务
  → 完成订单
```

## 3. 开发环境与启动

### 3.1 版本

- JDK：21.0.12 LTS
- Maven：3.9.16
- Spring Boot：3.5.10
- 前端：Vue 3 + TypeScript + Art Design Pro
- 前端包管理：pnpm 10（通过 npx 调用）
- 后端端口：8080
- 前端端口：3006

### 3.2 Windows 启动命令

在项目根目录打开 PowerShell：

```powershell
. .\use-tools.ps1
```

启动后端：

```powershell
Set-Location .\backend
mvn spring-boot:run
```

启动前端：

```powershell
Set-Location .\admin-web
npx --yes pnpm@10 install
npx --yes pnpm@10 dev
```

访问地址：`http://localhost:3006`

启动微信小程序开发构建：

```powershell
Set-Location .\miniapp
npm install
npm run dev:mp-weixin
```

微信开发者工具导入 `miniapp/dist/dev/mp-weixin`。需要一次性生成稳定构建时运行：

```powershell
npm run build:mp-weixin:dev
```

并导入 `miniapp/dist/build/mp-weixin`。自定义导航栏源文件位于 `miniapp/custom-tab-bar/`，构建脚本会同步到输出目录；若只修改导航栏，可运行 `node scripts/copy-wechat-tabbar.mjs dev`。

小程序请求地址位于 `miniapp/src/config/env.ts`。真机预览不能使用 `127.0.0.1` 访问电脑后端，需要改为电脑局域网 IP，并确保手机和电脑处于同一网络、防火墙允许访问 8080 端口。

前端本地代理配置位于：

- `admin-web/.env.development.local`
- API 代理目标：`http://localhost:8080`
- `/api` 和 `/uploads` 均由 Vite 转发到后端

## 5. 已完成功能

### 5.1 RBAC 与系统管理

- 用户新增、编辑、启用、禁用、重置密码
- 用户分配角色
- 角色新增、编辑、启用、禁用、删除
- 角色分配目录、菜单和按钮权限
- 菜单、目录、按钮权限 CRUD
- 菜单图标选择
- 登录日志和操作日志
- 禁止删除或禁用最后一个超级管理员
- 接口使用具体权限编码校验，不只判断 admin 角色
- 前端动态菜单和按钮权限隔离

核心权限编码示例：

```text
system:user:create
system:user:update
system:role:assign
business:product:create
business:order:status
business:dispatch:respond
```

### 5.2 游戏与陪玩师

- 游戏 CRUD、启停
- 游戏位置维护
- 陪玩师标签维护
- 陪玩师资料、游戏资料、擅长位置、主位置
- 头像、封面、段位证明、照片、视频、语音等媒体资料
- 陪玩师审核
- 工作状态管理
- 审核和工作状态日志
- 三角洲行动、无畏契约演示数据

主要业务规则：

- 只有审核通过且启用的陪玩师可以进入可接单状态
- 已被陪玩师使用的位置不能删除
- 游戏被陪玩师或商品使用时不能直接删除
- 上架商品引用的游戏不能禁用

### 5.3 文件上传

- 统一上传接口：`POST /api/file/upload`
- 本地保存目录：`backend/data/uploads/年/月/`
- 数据库只保存 `/uploads/...` 地址
- 支持图片、视频、音频和 PDF 证明材料
- 默认最大 20MB
- 上传需要登录并记录操作日志
- 前端统一上传组件支持预览、更换、移除和手填地址

存储接口已经抽象为 `FileStorage`。未来切换 OSS 时新增 OSS 实现即可，不要修改业务表字段。

### 5.4 商品与套餐

商品统一采用 SPU/SKU 模型：

- `SERVICE`：单项服务
- `PACKAGE`：平台套餐

已实现：

- 商品分类树
- 基础服务 CRUD
- 商品 SPU CRUD
- 多 SKU、售价、划线价、计价单位、购买范围、库存、服务时长
- 草稿、上架、下架
- 平台套餐组合多个基础服务
- 套餐服务数量和计量单位
- 套餐有效天数和每人限购
- 商品复制并自动生成新编码
- 游戏、分类、服务和 SKU 完整性上架校验

主要规则：

- 单项服务必须绑定一个基础服务
- 平台套餐至少包含两个不同基础服务
- 商品只能选择末级分类
- 商品、分类和基础服务必须属于同一游戏
- 至少存在一个启用 SKU 才能上架
- 上架商品禁止直接编辑和删除
- 被上架商品引用的分类或基础服务不能禁用
- 被商品引用的分类或基础服务不能删除

### 5.5 编码自动生成

- 游戏编码
- 游戏位置编码
- 标签编码
- 分类编码
- 基础服务编码
- 商品编码
- SKU 编码

工具文件：`admin-web/src/utils/business-code.ts`

### 5.6 订单中心

- 后台创建订单
- 选择用户、上架商品和 SKU
- 自动生成订单号
- 保存联系人、游戏账号、昵称、区服、段位和服务要求
- 创建订单时固化商品、SKU、成交价格、套餐服务组成快照
- 限量库存下单扣减，取消订单返还
- 订单详情、商品快照、游戏资料、状态时间线

当前状态机：

```text
PENDING_PAYMENT 待支付
  → WAIT_ASSIGN 待派单
  → ASSIGNED 已派单
  → IN_SERVICE 服务中
  → COMPLETED 已完成
```

允许取消的状态：待支付、待派单、已派单。服务开始后暂不允许直接取消。

目前“确认收款”是后台人工状态操作，不是真实支付回调。

### 5.7 派单与接单

- 指定派单
- 公开抢单
- 自动筛选候选陪玩师
- 候选人匹配分、评分、当前进行中订单数
- 后台模拟接受、拒绝
- 所有候选人拒绝后任务结束
- 查询任务时自动判定超时
- 取消派单
- 拒绝、超时、取消后重新派单
- 接单成功后订单自动变为已派单
- 接单后陪玩师变为忙碌
- 订单完成或取消后释放陪玩师状态
- 派单候选人和操作时间线

候选筛选条件：

- 陪玩师已启用且审核通过
- 陪玩师配置了订单对应游戏且游戏资料启用
- 默认只选择工作状态为 AVAILABLE 的陪玩师
- 进行中订单数不能超过派单规则

同一个派单任务的接单使用数据库条件更新：只有 `DISPATCHING` 状态可被首位接受者更新为 `ACCEPTED`，后续接受请求失败。

## 9. 已知限制与风险

1. 当前使用 H2 文件数据库，不是生产数据库。
2. 钱包支付、退款和陪玩师结算为站内模拟闭环，尚未接入微信支付、真实退款渠道和真实打款。
3. 派单超时采用访问列表/详情时的惰性判定，没有独立调度任务。
4. 同一派单任务只能有一个接单赢家；但不同任务同时分配同一陪玩师的跨任务并发锁还需要加强。
5. 订单表支持多明细，但当前创建接口一期只创建一个 SKU 明细。
6. 订单商品快照已保护历史展示，但商品编辑会删除并重建 SKU，历史订单不要再依赖实时 SKU。
7. 旧的 `/api/business/order/{id}/assign` 可以绕过新派单流程，建议下一步删除或限制。
8. 文件上传目前主要根据扩展名校验，生产环境还需要 MIME、文件头、安全扫描和鉴黄。
9. 上传文件删除后没有孤儿文件清理任务。
10. 当前表结构没有系统性添加外键，业务完整性主要由服务层维护。
11. 后台页面部分沿用模板示例模块，业务菜单以动态后端菜单为准。
12. 项目生产配置仍需重新检查域名、跨域、JWT 密钥、数据库、上传目录和日志策略。
13. 陪玩师只能配置资料、游戏、位置、标签和媒体，尚不能配置本人提供的服务、个人价格或服务上下架状态。

### 14.6 已确认但尚未编码的转单/炸单规则

- 一个订单可以有多个接单成员，并支持某一名成员单独转给另一名成员；未参与转单的其他成员继续履约，不随整组切换。例如 `A+B → C+B → D+B`，责任链只记录 `A→C→D`，B 的成员关系不变。
- 转单和炸单只能在服务过程中申请，用户或当前在役陪玩成员都可以发起；发起申请不等于审核通过，也不等于责任已经认定。
- 两类申请统一进入平台审核。申请至少记录 `申请类型`、`申请人类型`、`申请人 ID`、`原因`、`凭证`、`申请时在役批次/成员快照` 和 `审核状态`，保证后续换人后仍能还原现场。
- 审核状态建议统一为 `PENDING`、`APPROVED`、`REJECTED`、`CANCELLED`；平台审核必须记录审核人、审核时间、审核意见。审核中的申请不能直接生成扣款、补偿或责任流水。
- 转单申请必须明确 `source_order_member_id`。审核通过后只为这个成员席位进入补位派单；原成员在接替人实际接单前仍保留履约责任，不能因为提交申请就立即退出。接替成功后新增成员关系，并建立 `原成员 → 新成员` 的不可变转单关系；审核驳回则原成员继续履约。
- 炸单申请审核通过后才终止本次服务、冻结正常收益结算并进入责任判定；审核驳回则恢复服务。申请人身份与责任人身份必须分离，用户发起不能自动判定陪玩有责，陪玩发起也不能自动免责。
- 发生转单但最终成功结单时，只沿发生过转单的成员链结算“首位成员扣款转给该链最终接替人”；未转单成员不参与这笔承接补偿，不能把补偿平均发给整个最终在役组。
- 最终未成功结单时，不生成成功承接补偿；此时按最终在役成员逐人计算 20%，其中未发生转单但仍在役的成员也属于最终在役成员。
- 此前讨论的中间责任比例为每人 16%，中间组扣款归平台；其精确触发条件和计费基数仍需在编码前确认，不能与最终组 20% 默认重复计罚。
- 多人履约只约束当前在役成员，不要求已经被接替的历史成员提交完成凭证；历史成员通过各自的成员转单链参与后续责任结算。
- “16% 和 20% 的精确计费基数”“客户主动退单与服务炸单是否同一失败类型”仍需在编码 V43 前确认，并通过不可变责任流水记录。

## 15. V42 统一订单与多人结算模型

- `pw_trade_order` 只保存所有交易共有的编号、用户、业务类型、交易状态、金额、支付退款状态和时间；当前业务类型为 `PLAYER_SERVICE`、`WALLET_RECHARGE`。
- `pw_service_order` 保存陪玩人数、指定陪玩、等级快照、联系方式和履约状态；`pw_recharge_order` 继续保存充值套餐、赠送金额等充值专属字段，并通过 `trade_order_id` 关联主单。
- `pw_trade_payment` 统一承载陪玩支付和充值支付，旧 `pw_order_payment` 已迁移并移除。
- `pw_order_member` 是陪玩订单成员的唯一归属来源；旧 `pw_order` 和 `assigned_player_id` 已移除。
- `pw_order_settlement` 是单订单结算主单，`pw_order_settlement_detail` 记录平台佣金和每位成员收入，`pw_platform_ledger` 记录平台资金，`pw_player_earning` 通过 `order_member_id` 唯一关联成员收益。
- 当前多人策略为：先按规则从订单实付金额计算一次平台佣金，再将剩余金额等分给所有 `COMPLETED` 成员；除最后一人外向下保留两位，最后一人承接尾差，保证平台金额与所有成员收入之和严格等于订单实付金额。
- 转单、炸单属于陪玩服务分支，后续在 V43 增加责任链和处罚/赔付流水；不会污染充值等其他交易类型，也不需要重新改交易主表。
- V43 的异常申请建议使用 `pw_service_exception_request` 承载 `TRANSFER`、`ABORT` 两种申请；转单申请保存 `source_order_member_id`。审核通过并由接替人接单后，再向 `pw_service_member_transfer` 写入 `from_order_member_id`、`to_order_member_id`，形成可连续追溯的逐人转单链。责任认定继续独立保存，避免把“申请”“审核”“接替”“判责”“扣款”混为一个状态。
- 多人履约同样属于陪玩服务分支。V43 应增加成员级履约记录，并把套餐快照中的履约模式保存为 `ALL_MEMBERS`；订单级服务状态只聚合最终在役组成员状态。
- 转单后的成功结单与失败结单走两套资金规则：成功时，每条发生过转单的成员链分别把首位成员扣款补偿给链尾成员；失败不产生该补偿，当前最终在役成员按人承担 20%。
